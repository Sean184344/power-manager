# M3 crossing and reset contract

M3 adds `power_manager_cdc.sv` around the unchanged synchronous core. There are
three clock inputs: the always-on controller, the managed domain (which may
stop), and an always-running wake source. The testbench uses two independent
oscillators: AON and a raw managed oscillator. The latter also clocks the wake
source and an external clock-controller model; its gated output clocks the
managed workload. A wake producer must not depend on the stopped managed clock.

## Interfaces and handshakes

- Sleep is an AON-synchronous level. The producer holds it until accepted and
  samples it low to rearm; `sleep_ready_o` indicates the wrapper can start a new
  attempt. An accepted attempt consumes the request even if aborted. The wrapper
  retains that rule while masking requests during handshake cleanup.
- Wake is a one-source-cycle pulse asserted only when `wake_ready_o` is high.
  The source captures it as a held request. Two destination flops synchronize
  the request; the destination generates one AON pulse and raises an ack.
  Two source flops return the ack. Request and ack must both clear before the
  next event. This captures pulses shorter than an AON period when sampled by
  the source; arbitrary unsampled asynchronous pulses are not supported.
- Quiesce is a four-phase level handshake. AON holds the block request high;
  the managed domain synchronizes it, stops admission, finishes accepted work,
  then holds ack high. AON synchronizes ack before allowing ISOLATE. On abort or
  return to RUN, the wrapper still waits for ack before releasing its request.
  A new attempt waits for ack low and confirmation that domain blocking cleared.
  This prevents old acks from completing a later attempt. Work may still be
  accepted during the outbound synchronization delay and must also be drained.
- Clock readiness is a held asynchronous acknowledgement from an external clock
  controller. It must fall after disable and rise only when the requested clock
  is usable. AON synchronizes this level. The wrapper holds disable until it
  observes ready low before reasserting enable, so a quick wake cannot reuse stale
  ready. The external controller must respond to held requests; it must not
  require a continuously running managed clock to detect enable.

`active_o` reports core RUN, not instant domain admission: request cleanup and
synchronizer delays can keep `domain_block_work_o` high after RUN. Work admission
uses the managed-domain block output. On a recoverable drain timeout, the core
returns to RUN and records fault; the wrapper completes quiescing before reopening
admission. This preserves pending work and handshake freshness.

Two-flop synchronizers are marked `ASYNC_REG`. Only single-bit held control
signals cross; transaction IDs and data stay local to the workload. First stages
have no functional fanout except their second stages. No clock is generated by
production RTL; `clock_req_o` is a logical request to an implementation-specific
clock controller.

## Reset and bounds

One global active-low asynchronous reset asserts into all domains. Each domain
has its own two-flop synchronous release. A stopped clock keeps its reset asserted
until edges resume. Reset selects START, requests the clock on, isolates outputs,
blocks the managed domain, and cancels outstanding wake/work transactions.
Independent domain-only reset is outside this contract; it requires a separate
recovery protocol. Reset must meet the implementation's minimum assertion width.

Timeouts count AON cycles, including synchronization and external response delay.
The wrapper default is 64 cycles; an implementation must budget for the slowest
clock ratio, work latency, request/ack propagation and reset release. Too small a
bound may cause a safe drain abort or a START fault. Successful event priority
remains the synchronous core's priority after events arrive in AON; simultaneous
physical events in different domains have no guaranteed arrival order.

The design follows the full-handshake reuse principle described in
[AMD's XPM handshake documentation](https://docs.amd.com/r/2023.2-English/ug1344-versal-architecture-libraries/XPM_CDC_HANDSHAKE)
and per-domain reset synchronization guidance in
[Intel's reset design recommendations](https://www.intel.com/content/www/us/en/docs/programmable/683082/25-1/use-synchronous-resets.html).
This is original educational RTL, not an instantiation or certification of vendor IP.
Simulation checks protocol sequencing and reset behavior; it does not model
metastability, prove MTBF, validate placement/constraints, or provide CDC/RDC signoff.

## Verification results and replay

The matrix uses a 10 ns AON period, source periods of 6, 10, 14 and 26 ns,
source phase offsets of 0, 1 and 4 ns, and clock startup delays of 1 and 7 source
cycles. All 24 configurations pass all 18 required directed scenario checks:

- Repeated wake delivery, busy sleep, held sleep requests and request rearming.
- Work accepted during the outbound block-request crossing, delayed quiesce
  acknowledgement, and wake abort followed by rearming during handshake cleanup.
- Drain timeout, stale ready during quick wake, and missing startup readiness.
- Reset in each of RUN, DRAIN, ISOLATE, SLEEP, START, RELEASE and FAULT.
- Reset with a captured but undelivered wake, followed by successful bridge reuse.

Each configuration accounts for five work transactions: three completed and two
explicitly canceled by reset. Nineteen wake events are captured: eighteen are
delivered and one is explicitly canceled by reset. No work or wake remains
unaccounted for. The 6 ns source-clock runs exercise source pulses shorter than
the 10 ns AON period. Local reset monitors check that release occurs on the second
local rising edge; the managed clock is actually stopped in the sleep tests.

The scoreboard's asynchronous reset process is separate from its delayed output
sampling process. This prevents a reset occurring during the sampling delay from
being missed. Both the earlier M2 suite and M3 exercise the corrected scoreboard.

Coverage records directed scenarios after their checks, plus the observed state
for reset targets. It is a finite scenario matrix, not exhaustive crossing-phase
coverage. Source and wake clocks share the raw oscillator in this environment;
independently sweeping a third oscillator is outside the current evidence.
